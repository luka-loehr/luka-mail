## Summary

`SmtpClient` retained pre-TLS buffered bytes across `STARTTLS` upgrades (`CVE-2011-0411` response injection), `encodeHeaderWords` emitted single-line `=?UTF-8?B?...?=` tokens exceeding the RFC 2047 75-char / RFC 5322 998-byte line limits on long UTF-8 subjects, and `ImapClient.readResponse` allocated `new Uint8Array(size)` directly from untrusted `{size}` server literals.

## Evidence

- `src/worker/smtp.ts`: `SmtpClient.buffer` persisted across `transport.startTls()` without rejecting pipelined plaintext bytes after `220 Ready to start TLS`.
- `src/worker/mime.ts`: `encodeHeaderWords` base64-encoded the entire header value into one unbroken token.
- `src/worker/imap.ts`: `readResponse` passed untrusted `{size}` straight to `readBytes(size)` and `fill()` copied the full buffer on every chunk.

## Risk

MITM/malicious SMTP relay plaintext response injection across STARTTLS, outbound DKIM/MTA rejection on long non-ASCII subjects, and Worker isolate OOM (`128 MB`) from a rogue external IMAP server advertising `{2147483647}`.

## Fix and current state

Fixed in `26f4d72` (`src/worker/smtp.ts`, `src/worker/mime.ts`, `src/worker/imap.ts`): `SmtpClient` now aborts `STARTTLS` if plaintext bytes follow `220`, resets `SmtpClient` post-handshake, supports implicit TLS on port 465 (`secureTransport: "on"`), and bounds reply line lengths/counts; `encodeHeaderWords` chunks UTF-8 byte slices at `<= 45` bytes into folded RFC 2047 words (`<= 75` chars each); `ImapClient` enforces `MAX_LITERAL_BYTES = 16 MiB`, `MAX_LINE_BYTES`, `MAX_UNTAGGED_RESPONSES`, and linear chunk assembly.

## How to verify

- `npm test -- tests/security-hardening-v2.test.ts tests/smtp.test.ts tests/imap.test.ts tests/mime.test.ts`: verifies pipelined post-`220` STARTTLS bytes throw immediately, 240-char UTF-8 subjects fold under 76 chars per word, and oversized IMAP literals fail fast.
